What this folder is

One place that answers, for any web project: what are we producing, who produces it, who signs it off, and what does "done" mean?

It has five parts.

  1. The workflow map — the one-page client-facing visual of the whole process (below).
  2. The operating process — phases, gates, roles and rules (this document).
  3. The templates — a blank, fill-in document for each of the eleven deliverables, in templates/.
  4. The canonical production guide — end-to-end-seo-website-production-process.md, adopted 3 August 2026. Twenty-seven phases, three actors (consultant · copywriter · Claude Code), one prompt and one approval gate per phase. This is the operating detail for SEO-led builds. Its costed seven-week schedule is the companion lean-end-to-end-seo-website-process.md.
  5. The SOP process map — sop-process-map.html. The whole twenty-seven-phase guide compressed to nine stages and six gates on one screen. Open this first; open the guide when you need the prompt.

The reasoning behind the sequence — why words come before boxes, why the shared stylesheet is built when it is, what the research says — is not repeated here. It lives in the house playbook: Research/Website Design Process/website-production-sequence-playbook-2026-08-02.md. Read that once. Use this folder every day.

Starting a new project

1.  Copy the whole _project-starter folder:

    cp -R "_project-starter" \
          "../../Web Design Projects/<Client Name>/00-process"

2.  Open 01-website-brief.md. Fill it in during or straight after the
    kickoff call. Nothing else starts until it is signed off.

3.  Work down the numbered files in order. Each one names the next.

4.  Foundations (F1–F3) are copied only on the first project for a
    client. On later projects, link to the existing ones instead.

The starter folder holds a numbered copy of every template plus a PROJECT-LOG.md for decisions, and a checklist for the three gates.

The rules that are not negotiable

These are the ones that cost us money or quality when they slip. Each links to where it is written up in full.

  1. Real words before layout. No lorem ipsum, ever — not even in a lo-fi wireframe. Layout built on fake copy breaks the day the real (and in German, longer) copy arrives.
  2. Low cognitive load is the default standard. Every page project follows the low-cognitive-load-design and low-cognitive-load-copy skills unless a written exception exists.
  3. Plain language, no jargon. Client-facing copy must be understood at a glance by a fifteen-year-old. Tenth grade is the ceiling.
  4. One shared stylesheet. Anything appearing on two or more pages is defined once, centrally. Per-page duplicated CSS is what causes cross-page drift.
  5. Hero is the first two thirds of the viewport — about 66vh, never 100vh, so the next section peeks above the fold.
  6. Fidelity gate order. Lo-fi → mid-fi → production, with approval at each. Production build needs an explicit go-live or approval-plus-build instruction.
  7. SEO pages pass the ship gate. No SEO or service landing page goes live without the 242-item seo-page-qa-gate. Zero blockers permitted.
  8. Verify by render, not by grep. A clean source search is not proof a style is right. Check computed styles in a live browser.
  9. GitHub, never Vercel. Code and live links go through GitHub / GitHub Pages.
  10. Two revision rounds per gate. Round three is a priced change request.

On a small project one person holds several roles. The roles still exist — they tell you which hat you are wearing and which questions are legitimately yours to answer.

Scaling past one page

Design effort scales with the number of page types. Content effort scales with the number of pages.

For a 20-page site you do not produce 20 wireframes. You produce one per page type — typically 4 to 6 — get those approved, and then the remaining 14 pages are population, not design. The Page Blueprint (02) is where the page-type inventory is set, and getting it right there is what makes a large site affordable.
